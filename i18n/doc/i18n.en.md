# Orbiter Chinese Localisation (i18n) — Architecture

All translation data is **externalised as UTF-8 `.po` files** (a `.po` subset:
`msgid`/`msgstr`/`msgctxt`). The core and the plugins load them at run time via
`oapiRegisterTranslationCatalog`; no large Chinese translation tables are
compiled into the code any more. Correcting or extending a translation only
requires editing the `.po` files in the installation directory — no rebuild.

## Directory layout

```
i18n/
├── locales/zh_CN/           translations loaded at run time (installed to <Orbiter>/i18n/locales/zh_CN/)
│   ├── core.po              core UI (main program/MFD/dialogs/wreck messages)
│   ├── launchpad.po         Launchpad window texts
│   ├── scenario.po          scenario/folder descriptions (msgctxt = "scenario.description")
│   │                        and constellation names (msgctxt = "constellation")
│   ├── plugins.po           plugin/vessel module UI texts
│   └── d3d9client.po        D3D9Client settings dialog texts (loaded by the plugin)
├── core/                    core localisation implementation plus retained layout/algorithm data
│   ├── Localization.h/.cpp  translation tables, Tr/TrContext, language setting, encoding
│   │                        conversion, .po parser (RegisterTranslationCatalog), oapiTr exports
│   ├── MfdZh.inc            MFD Chinese layout offsets + built-in MFD alias table (not a translation table)
│   ├── InstrumentZh.inc     glass cockpit panel/HUD Chinese labels and font-size parameters (not a translation table)
│   ├── ZhCommon.inc         Chinese layout algorithms (fonts/measurement/right-aligned multi-column, not a translation table)
│   └── LaunchpadZh.inc      only the direct control-text logic of the Extra-tab "orbit stabilisation" dialog
├── d3d9client/              (the former D3D9ClientZh.inc has been externalised to d3d9client.po)
├── scneditor/EditorZh.inc   scenario editor dialog localisation logic (texts in plugins.po)
├── vessels/                 vessel module localisation logic (texts in plugins.po)
├── plugins/                 MFD button Chinese label arrays (the button atlas has no English text keys, so arrays are kept)
└── doc/i18n.md              this document (Chinese); i18n.en.md is the English version
```

## Run-time loading

1. **Core**: `InitLocalization()` builds the empty tables and calls
   `LoadBundledCatalogs()`, which loads `i18n/locales/zh_CN/core.po`,
   `launchpad.po`, `scenario.po` and `plugins.po` in order (paths relative to the
   game working directory). Missing files are skipped silently (that part is
   shown in English; start-up is unaffected).
2. **Plugins**: call `oapiRegisterTranslationCatalog(path)` in `InitModule()` to
   load their own `.po` file (e.g. D3D9Client loads
   `i18n/locales/zh_CN/d3d9client.po`). Plugins may also register single entries
   with `oapiRegisterTranslation`, or ship their own translation files.
3. **Installation**: CMake `install(DIRECTORY i18n/locales DESTINATION <install-root>/i18n)`;
   the distribution ships the `.po` files, so users can edit the `.po` files in
   the installation directory to fix/extend translations.

## .po file format (subset)

```po
# comment line
msgid "OpenOrbiter Launchpad"
msgstr "OpenOrbiter 启动器"

# context translation (same word, different meaning): distinguished by msgctxt
msgctxt "scenario.description"
msgid "<h1>Orbiter Challenges</h1> ..."
msgstr "<h1>轨道挑战</h1> ..."
```

- UTF-8 encoding (a BOM is tolerated); the escapes `\n`, `\t`, `\r`, `\"`, `\\`
  behave like C strings.
- Duplicate msgids: the last loaded entry wins (same behaviour as the old
  compiled-in table).
- `msgctxt` entries go to the context table and can only be queried via
  `oapiTrContext`/`orbiter::TrContext`; plain `msgid` entries go to the main
  table queried by `oapiTr`.

## Public API (SDK, see `Orbitersdk/include/OrbiterAPI.h`)

| Function | Description |
|---|---|
| `oapiTr(english)` | translate a UI string (English mode returns the original) |
| `oapiTrContext(context, english)` | context-aware translation |
| `oapiTrName(english)` / `oapiGetOriginalName(localized)` | name translation and reverse lookup |
| `oapiGetLocale()` | `"zh_CN"` / `"en"` |
| `oapiRegisterTranslation(locale, en, zh)` | register single entries at run time (add only, no overwrite) |
| `oapiRegisterTranslationCatalog(path)` | load a .po subset (supports msgctxt) |
| `oapiUtf8ToWide` / `oapiWideToUtf8` / `inline oapiUtf8ToWString` | UTF-8/UTF-16 conversion |
| `oapiZhActive()` | whether Chinese mode is active |

## Writing rules

- **English is the key**: `msgid` must be the English original exactly as it
  appears in the code (same case, punctuation and spaces); English mode never
  looks at the tables and is unaffected.
- **Placeholder order**: for templates containing `%s` etc., the number and
  order of placeholders in `msgstr` must match `msgid`.
- **Language checks**: use `oapiZhActive()` (plugins) or `orbiter::IsChinese()`
  (core); never compare translated texts.
- **UTF-8**: `.po` files and Chinese string literals in the sources are UTF-8;
  use `oapiUtf8ToWString`/`oapiWideToUtf8` for Win32 wide-character APIs.
- **Chinese HTML pages**: URLDESC scenario descriptions use `*_zh.htm` Chinese
  pages (e.g. `CurrentState_img_zh.htm`). When saving as UTF-8 they must contain
  `<meta http-equiv="Content-Type" content="text/html; charset=utf-8">`,
  otherwise the IE control decodes them as the system ANSI code page and shows
  garbled text.
- **Lua scripts**: built-in scripts (the Lua loaded via the scenario `Script`
  field, e.g. Challenges/Demos tutorials) query the translation table through
  the Lua global `tr("english")`; the texts live in `scripts.po`. Note that a
  trailing `\` line continuation in Lua **keeps the newline**, so multi-line
  msgids must contain those newlines (e.g. `Flight challenge:\n\n...`).

## Unified text encoding layer (TextCodec)

Rule: **there is exactly one text encoding inside the program: UTF-8**. Text
entering the program (files, legacy ANSI API) is converted once by the unified
layer; text leaving the program for a Win32 API always uses the Wide (Unicode)
variant. The core implementation is in `i18n/core/Localization.h/.cpp`:

| Function | Purpose |
|---|---|
| `orbiter::IsValidUtf8` / `DetectTextEncoding` | UTF-8 validation and encoding detection (UTF-8 BOM / UTF-16 LE/BE BOM / ANSI fallback) |
| `orbiter::ReadTextFileUtf8` | read a text file of any encoding and convert it to UTF-8 (the only file text reader) |
| `orbiter::LocalToUtf8` | system ANSI code page -> UTF-8 (data written by legacy tools) |
| `orbiter::LocalToWide` | UTF-8 -> UTF-16 (invalid UTF-8 falls back to ANSI decoding for legacy plugins) |
| `orbiter::Utf8ToLatin1` / `Latin1ToUtf8` | UTF-8 <-> ISO-8859-1/Windows-1252 (single-byte render paths of the graphics clients) |

The corresponding D3D9Client renderer implementation is centralised in
`OVP/D3D9Client/TextCodec.inc` (`Utf8ToCp1252`, `Utf8ToWideLocal`,
`NeedsUnicodeText`); D3D9Pad, GDIPad and TileLabel all use that shared
implementation.

**Rule**: outside the TextCodec layer itself, code must not call
`MultiByteToWideChar`/`WideCharToMultiByte` directly, and non-ASCII text must
not be passed to the ANSI Win32 text APIs (`SetWindowTextA`, `TextOutA`,
`SendDlgItemMessageA`, ...).

## Run-time layout data (layout.ini)

The **layout values** (not the algorithms) of the Chinese UI are externalised
into a run-time editable data file; changes need no rebuild:

```
i18n/layout/zh_CN/layout.ini      # installed to <Orbiter>/i18n/layout/zh_CN/layout.ini
```

- INI subset: `[section]` + `key = value`, `;`/`#` comments; values may be
  single- or double-quoted
- Loading: `InitLocalization`/`SetLanguage` load the file in Chinese mode only;
  English mode does not load it. When the file is missing, the built-in defaults
  in the code are used (identical to the historical compiled-in values, so
  deleting the file restores the previous behaviour)
- API: core `orbiter::LayoutInt/LayoutFloat/LayoutString`; plugins
  `oapiGetLayoutInt/Float/String`
- Already externalised: MFD Chinese offsets (`[mfd.landing]` etc.), panel font
  size specs (`[panel.font]`), panel/HUD texts (`[panel.buttons]`/`[hud]`),
  MFD button labels (`[mfd.*.buttons]`), GenericCamera offsets
  (`[mfd.genericcamera]`)
- The getters in the `i18n/*Zh.inc` files still carry the default values;
  algorithms/drawing flows (e.g. `ZhCommon.inc`) must stay in code and are not
  layout data

## Dialog layout adaptation (official layout + offset)

Dialogs other than MFDs (scenario editor vessel pages, Launchpad extra pages,
...) follow the same "official layout + Chinese offset" rule:

- The RC resources keep the official English layout; English mode is completely
  unaffected
- In Chinese mode, when a dialog is initialised, control texts are translated
  with `oapiTr` and then adapted by the SDK layout APIs using the **measured**
  text width/height:
  - `oapiZhFitControlText(hDlg, ctrlId, padX)` — translate one control and
    widen it when needed (left edge and vertical position are preserved)
  - `oapiZhFitControlRow(hDlg, ctrlIds, count, padX, gap, startX)` — translate
    and repack one row of controls left-to-right (so wider Chinese buttons do
    not overlap)
  - `oapiZhFitControlHeight(hDlg, ctrlId, padY)` — grow only the height
  - `oapiZhFitDialogButtons(hDlg, padX, padY)` — translate all push buttons of
    a dialog and grow them; a row whose widened buttons would overlap is
    repacked left-to-right automatically
  - `oapiZhOffsetControls(hDlg, ctrlIds, count, dx, dy)` /
    `oapiZhOffsetWindow(hCtrl, dx, dy)` — apply layout-INI offsets to controls
- The offset values (`padX`/`padY`/`gap`/row positions) come from the
  `[dialog.*]` sections of `layout.ini`; defaults are used when absent
- Applied to: Shuttle-A vessel editor animation page
  (`[dialog.shuttle_a_anim]`), scenario editor secondary-parameter page
  (`[dialog.scneditor.secondary]`), vessel editor pages
  (`[dialog.vessel_pages]`)
- New dialog adaptations should reuse the APIs above; do not hard-code Chinese
  widths/coordinates in code

## i18n lint (encoding and localisation rule checks)

`tools/i18n_lint.ps1` enforces the following rules and can be used as a CI step
(exit code 1 = violations):

1. Source and data text files must be valid UTF-8
2. Source code must not contain hard-coded Chinese string literals
   (translations belong in `.po` files)
3. Non-ASCII text must not be used with the ANSI Win32 text APIs

Usage: `powershell -ExecutionPolicy Bypass -File tools/i18n_lint.ps1`.
Intentional exceptions (e.g. language endonyms in the language selector) are
marked with `// lint:allow-cjk` at the end of the line.

## Data that must stay in code (cannot be data-driven)

- `i18n/core/ZhCommon.inc`: the Chinese layout **algorithms** (font cache,
  measurement, right-aligned multi-column layout, panel/HUD flows); all of their
  layout **values** have been moved to `layout.ini`.
- `i18n/core/MfdZh.inc`, `InstrumentZh.inc`: only getters (default values) plus
  button index/alias mapping logic.
- `LaunchpadZh.inc` section B: direct control texts of the Extra-tab "orbit
  stabilisation" dialog (tied to Win32 control IDs, still compile-time data and
  may be moved to `launchpad.po` later).
- `i18n/scneditor/EditorZh.inc`, `i18n/vessels/*Zh.inc`,
  `i18n/plugins/*Zh.inc`: dialog layout **logic** (coordinate calculations
  based on `SetWindowPos`); a few numeric constants are coupled into that
  logic; when fine-tuning is needed, migrate those constants to `layout.ini`
  step by step.
- `Html/Scenarios/CurrentState*_zh.htm`: Chinese HTML pages for scenario
  descriptions.

## Migration log (2026-11)

- The former compile-time translation tables (`g_translations` array in
  `Localization.cpp` plus the `DialogZh/LaunchpadZh/ScenarioDescZh/ScenarioScnZh/
  WreckMsgZh/PluginZh/D3D9ClientZh` data) have been fully exported to
  `i18n/locales/zh_CN/*.po` and are loaded at run time; the corresponding
  `.inc` data files have been removed.
- Plugin-private `wchar_t` mapping tables were migrated to `oapiTr` + `.po`
  data; the modules only keep the localisation logic.
- Duplicate UTF-8 conversion helpers were unified into the SDK's
  `oapiUtf8ToWString`.
- Translation conflicts (same word, different meanings) are resolved with
  `msgctxt` context translations; duplicated names have been unified.
- Wreck/impact messages were changed to `.po` templates (`core.po`).
- Unified text encoding layer (TextCodec): added `IsValidUtf8`/
  `DetectTextEncoding`/`ReadTextFileUtf8`/`LocalToUtf8`/`LocalToWide`/
  `Utf8ToLatin1`/`Latin1ToUtf8`; scattered `MultiByteToWideChar`/
  `WideCharToMultiByte` calls were removed from the sources (D3D9Client is
  centralised in `TextCodec.inc`).
- Layout data externalisation (2026-11): added `i18n/core/Layout.*`,
  `i18n/layout/zh_CN/layout.ini` and the `oapiGetLayout*` SDK interfaces; MFD
  offsets, panel font sizes/button/HUD texts and MFD button labels moved out of
  the code.
- Scenario description reading/translation is handled by
  `orbiter::ReadScenarioDescription` (i18n module); the official
  `TabScenario.cpp` only contains the API call; long lines are no longer split
  by the fixed line buffer.
- The relativity scenario files were originally GBK-encoded (garbled text) and
  have been converted to UTF-8; all 392 data text files were verified as UTF-8.

## Not localised / intentionally English

- Texts in the HUD texture character set (the cockpit HUD uses bitmap glyphs;
  use `oapiZhHudText` overlays where needed).
- Some third-party plugins (XRSound, TerrainToolKit, ...) have no localised UI.
- In URLDESC mode a few built-in CHM help pages other than `CurrentState` have
  no Chinese copy.
